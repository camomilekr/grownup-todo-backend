# 참조 — 규약이 이렇게 생긴 이유

`.claude/rules/core.md`의 조항 대부분은 실제로 한 번 데인 자리다. 규약을 고치거나 예외를 두려 할 때 여기서 근거를 확인한다. **근거를 모르고 지운 조항이 같은 사고를 다시 낸다.**

## 프로세스 과적용 — 좁은 작업에 전체 프로세스를 씌웠다

2026-07-30에 사용자가 "개발 속도가 느려졌다"고 지적해 측정했다.

| 측정 | 값 |
|---|---|
| 세션마다 읽으라고 강제한 룰 | **1,495줄**. 에이전트 넷이 각각 읽어 루프당 약 6,000줄 |
| PR #11(FlashList prop **한 줄** 수정) 소요 | **56분**. 그중 계획서 대기 15분 |
| PR #11이 남긴 문서 | 계획서 403줄 + 기록 409줄 = **812줄** (코드 변경 24줄) |
| 머지된 PR 11개의 성격 | 코드 5개 vs **프로세스 문서 6개** |
| `npm run verify` | **12초** — 관문은 병목이 아니었다 |

리뷰 지적을 심각도로 세면 경계가 뚜렷했다.

| 작업 | 성격 | 리뷰 결과 |
|---|---|---|
| ios-accessibility (PR #5) | 여러 컴포넌트를 훑는 횡단 작업 | **blocker 1, major 6** |
| steps-no-manual-toggle (PR #8) | 관심사 하나 | blocker 0, major 0, minor 1 |
| fix-added-todo-not-visible (PR #11) | prop 한 줄 | blocker 0, major 0, minor 1 |

**좁은 작업 두 건에서 major 이상이 0이었다.** 그런데 당시 규약은 "애매하면 쓰는 쪽으로 기운다"를 두 문서에 못박아 두어 넓은 작업과 좁은 작업이 같은 무게를 받았다.

여기서 나온 것:

- **티어 조건표**(`core.md`) — 애매함이 아니라 조건을 세어서 갈린다
- **문서를 계층화**했다 — 항상 주입되는 `.claude/rules/`(약 330줄)와 필요할 때만 읽는 `.claude/ref/`
- **`.claude/rules/*.md`는 자동 주입된다는 사실.** 그런데 당시 `AGENTS.md`와 에이전트 정의 셋이 모두 "전부 **읽어라**"고 지시해, 에이전트들이 **이미 컨텍스트에 있는 1,495줄을 `Read`로 다시 읽고** 있었다
- **절차를 스크립트로 옮겼다**(`.claude/scripts/`) — 문서로 강제하던 순서를 코드가 지킨다. 워크트리 준비 12초, 지문 계산 1초
- **계획서 80줄·기록 100줄 상한**

## 같은 요청이 두 잡에 들어가 세 번 충돌했다

2026-07-27 `feature/ios-accessibility`. 두 잡이 각자의 `developer`·`reviewer` 루프를 돌려 같은 파일을 쓰며 01:48, 02:29, 02:55 세 번 충돌했다. 결론이 우연히 같은 방향이라 합쳐졌을 뿐 보장은 없었다.

**어떻게 그렇게 됐는가가 중요하다.** 사용자가 요청을 두 번 보낸 것이 아니다. 한 세션이 요청을 받아 잡을 띄우고 워크트리를 만든 직후, **이미 열려 있던 다른 세션에 같은 작업을 "이어서 해 달라"고 지시**한 것이다. 받은 쪽은 그것이 재지시인지 첫 지시인지 알 방법이 없었다.

**워크트리 생성(01:35:30)과 첫 파일 쓰기(01:48:25) 사이에 13분의 공백**이 있었다. 그 세션의 `developer`가 룰과 `CONTEXT.md`를 읽는 동안이다. 그 사이 01:37에 다른 잡이 들여다보고 "커밋 0, 변경 0이니 아무도 작업하지 않는다"고 판단했다.

여기서 나온 것:

- **점유 표식을 워크트리를 만든 그 자리에서 남긴다** — `worktree-new.sh`가 자동으로 한다
- **"깨끗하다"를 "주인이 없다"로 읽지 않는다.** `npm install`이 돼 있다는 것 자체가 누군가 준비했다는 신호다
- **`TaskList`의 `No tasks found`는 근거가 되지 못한다.** 그 도구는 자기 잡의 태스크만 본다. 형제 잡은 `ls ~/.claude/jobs/`로 본다
- 지시하는 쪽은 진행 중인 작업을 다른 세션에 다시 맡기지 않는다. 맡기려면 먼저 원래 잡을 정지시킨다

부산물로 알게 된 것: **리뷰어가 둘이 된 것은 이득이었다.** 한쪽만 찾은 항목이 셋(blocker 1, major 2)이었다. 다만 이건 의도한 설계가 아니라 사고의 부산물이다 — 리뷰 다각화가 필요하면 같은 라운드에 리뷰어를 둘 띄우는 쪽이 안전하다.

## 지문이 신규 파일을 놓쳤다

2026-07-28 `feature/fix-added-todo-not-visible`. 신규 테스트 파일 232줄이 빠진 지문(`d5a9958c18dd`)을 먼저 찍었다. `git diff`는 추적되지 않는 파일을 보지 못하므로, **고정한 줄 알았던 것이 고정되지 않았다.** `git add -N` 뒤 다시 찍은 값(`714a08d4f5bf`)이 진짜 지문이었다.

`.claude/scripts/fingerprint.sh`가 `git add -N`을 품고 있다. **손으로 `git diff | shasum`을 찍지 마라.**

리뷰 중에 트리가 바뀐 일도 실제로 있었다(`feature/ios-accessibility`, 3라운드 검토 중 세 번). 그때 리뷰어가 판정 기준 지문을 보고에 적어 준 덕에 유효성을 확인할 수 있었다.

## `architect`를 건너뛰려 했다

2026-07-28 `feature/fix-added-todo-not-visible`. 오케스트레이터가 원인을 `TodoList.tsx` 한 곳으로 짚어 두고 "파일 하나로 끝나는 버그 수정"이라 읽었으나 사용자가 계획 단계를 요구해 되돌렸다. 결론은 같았지만 **계획서가 없었으면 놓쳤을 것이 둘 나왔다.**

- **추가 흐름을 끝까지 잇는 테스트가 하나도 없다**는 사실. 그래서 그 테스트가 단계 1로 세워져 **"상태 계층에는 결함이 없다"를 코드로 확정하는 판별기**가 됐다. 짐작이 틀렸다면 그 단계에서 드러났을 것이다
- **빈 목록에서의 첫 추가는 보정되지 않는다**는 판별 지문. 사용자에게 물을 질문이 여기서 나왔다

**계획 단계의 값어치는 "무엇을 고칠지"만이 아니라 "진단이 틀렸을 때 그것을 어디서 알아차릴지"에 있다.** 그래서 티어 1의 네 번째 조건이 "버그면 원인이 확정됐다"다.

같은 루프에서 `사용자가 완료 탭에 있었을 뿐이다`라는 후보도 열려 있었다 — 사실이면 버그가 아니어서 구현 전체가 헛일이 될 수 있었다. 물어서 배제한 뒤 진행했다.

## 알림 없이 멈춰 있었다

같은 루프에서 계획서를 15분 기다린 뒤 진단 확인 질문을 `AskUserQuestion`으로만 띄웠다. 사용자가 먼저 "왜 노티피케이션을 보내지 않았지?"라고 물어야 했다.

알림 채널에 대해 알게 된 것:

| 시점 | 도구 응답 | 모바일 도달 |
|---|---|---|
| 서브에이전트 완료 | `Terminal notification sent. Mobile push requested.` | 오지 않았다 |
| PR 완료 | `Not sent — this terminal is active` | (전송 자체가 스킵) |

**터미널 전송은 되고 모바일 전달만 막혀 있었다.** Claude 앱의 "채팅 응답 알림"이 꺼져 있던 것을 사용자가 발견해 켰다. 도구는 요청까지만 알려 주고 도달 여부를 돌려주지 않는다.

세 번째가 스킵된 것도 정보다 — **사용자가 터미널에 있으면 알림이 아예 나가지 않으므로** 보낼지 말지 재는 것 자체가 낭비다.

## 계획서가 틀렸음이 구현 중에 드러났다

같은 루프에서 `developer`가 근거를 대고 둘을 보고했고 오케스트레이터가 둘 다 받아들였다 — 시트 mock이 `onDismiss`를 부르지 않는 것, 테스트 라이브러리가 새 버전에서 쿼리 API 네 개를 한꺼번에 제거한 것(계획서가 제시한 대안도 함께 사라져 있었다).

> 이 사고는 이 저장소가 React Native 앱이던 시절에 일어났다. 지금은 NestJS 백엔드라 그 라이브러리를 쓰지 않지만, **"계획서가 제시한 대안이 이미 사라져 있었다"는 교훈은 그대로 유효하다** — 그래서 기록은 남긴다.

- **`developer`가 근거를 대고 다른 방식을 제안했다면 그 판단을 받아들인다.** 코드를 쥔 쪽이 더 잘 안다
- **단, 건드리는 파일 집합이 바뀌면 병렬 배치를 다시 봐야 한다**
- **계획서를 갱신한다.** 갱신하지 않으면 다음 트랙의 `developer`가 낡은 계획을 읽는다
- 계획이 통째로 흔들리면 루프를 멈추고 `architect`에게 다시 맡긴다. 흔들리는 계획을 붙잡고 라운드를 쌓는 것이 가장 비싸다
