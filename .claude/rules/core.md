# 개발 규약 — 핵심

**이 문서와 같은 폴더의 `*.md`는 세션 시작 시 자동으로 컨텍스트에 들어온다. 다시 `Read`하지 마라.** 이미 들고 있는 것을 다시 읽는 것이 이 루프에서 가장 값싼 낭비였다.

깊은 내용은 `.claude/ref/` 아래에 있고 **자동 주입되지 않는다.** 아래 표의 상황에 걸렸을 때만 읽는다.

| 참조 문서 | 언제 읽는가 |
|---|---|
| `.claude/ref/troubleshooting.md` | 명령이 실패했거나 증상의 원인을 모를 때 |
| `.claude/ref/testing-traps.md` | 테스트가 예상과 다르게 동작할 때. 통과만 하는 테스트를 의심할 때 |
| `.claude/ref/parallel.md` | 트랙을 나눠 병렬로 돌리기로 정한 뒤에만 |
| `.claude/ref/incidents.md` | 이 규약이 왜 이렇게 생겼는지 근거가 필요할 때 |

메인 세션은 **오케스트레이터**다. 직접 구현하지 않고 서브에이전트를 부르고 결과를 옮긴다. 정의는 `.claude/agents/`에 있다 — `architect`(계획), `developer`(구현), `reviewer`(검토).

## 티어 — 무게를 작업 크기에 맞춘다

**조건을 세어서 갈린다.** 애매함을 이유로 무거운 쪽으로 기울지 마라 — 좁은 작업에 전체 프로세스를 씌우는 것이 실제로 속도를 깎았다(`ref/incidents.md`의 "프로세스 과적용").

| 티어 | 조건 | 절차 |
|---|---|---|
| **0 · 직접** | `.claude/` 규칙·에이전트 정의, 문서, 설정값 한 줄, 오타, 조사·질문 답변 | 메인 세션이 직접 한다. 루프도 계획도 없다 |
| **1 · 가볍게** | 아래 넷을 **모두** 만족 | 브랜치만 만들고 → `developer` 1회 → `reviewer`(diff 한정) → 커밋·PR. **계획서와 기록을 만들지 않는다** |
| **2 · 전체** | 티어 1 조건 중 **하나라도** 어긋남 | `architect` 계획서 → 오케스트레이터 검증 → `developer`↔`reviewer` 루프 → 커밋·PR. 기록을 남긴다 |

티어 1의 네 조건:

1. 건드리는 `src/` 하위 폴더가 **2개 이하**다
2. **새 도메인 타입이나 영속화 형식 변경이 없다**
3. **횡단 관심사가 아니다** — 접근성, 보안, 알림 스케줄, 날짜 경계는 여기서 빠진다. 한 곳을 고치면 다른 곳이 어긋나는 종류라 독립 검토가 필요하다
4. 버그 수정이면 **원인이 확정됐다**

4번을 특히 조심해라. **수정 범위는 원인이 정한다.** 코드를 읽어 짐작한 것은 확정이 아니고, 확정되지 않은 원인으로 티어 1을 고르면 검토받지 않은 진단이 그대로 구현으로 넘어간다. 계획 단계의 값어치는 "무엇을 고칠지"만이 아니라 **"진단이 틀렸을 때 그것을 어디서 알아차릴지"**에 있다.

사용자가 "바로 고쳐 줘"라고 했으면 그 지시가 티어를 덮는다.

## 작업 공간

**기준 브랜치는 `develop`이다.** 브랜치는 `feature/{케밥케이스}`, PR도 `develop`으로 보낸다. `main`은 릴리스 절차 밖에서 손대지 않는다.

**`develop`에 직접 커밋·푸시하지 않는다.** 사용자가 그 브랜치를 명시해 요청한 경우에만 허용되고, 그 허가는 그 요청 한 번에만 유효하다. "커밋해 줘"만으로는 부족하다 — 브랜치를 말하지 않았다면 `develop`이 아니다.

```bash
# 티어 1 — 브랜치만
git switch develop && git pull && git switch -c feature/fix-midnight-rollover

# 티어 2 — 워크트리까지. 브랜치·복제·계획서·점유 표식을 한 번에 만든다
.claude/scripts/worktree-new.sh step-goal-presets
```

**워크트리 하나에 잡 하나.** 내가 만들지 않은 워크트리에서 작업하라는 지시를 받으면 에이전트를 부르기 전에 넷을 확인한다 — `docs/dev-loop/`의 점유 표식, `ls ~/.claude/jobs/`의 형제 잡, 60~90초 간격으로 두 번 찍은 지문, `ps -eo pid,args | grep {경로}`. **하나라도 걸리면 멈추고 사용자에게 묻는다.**

**"깨끗하다"를 "주인이 없다"로 읽지 마라.** 커밋 0, 변경 0은 "아직 안 썼다"이지 "주인이 없다"가 아니다. `TaskList`의 `No tasks found`도 근거가 되지 못한다 — 그 도구는 형제 잡을 보지 못한다.

**`Agent` 도구의 `isolation: "worktree"`를 쓰지 않는다.** 이 규약 밖의 경로에 워크트리를 만들어, `.claude/worktrees/` 아래를 전제한 설정(Jest 제외 패턴, IDE 프로젝트 인식)이 걸리지 않는다.

**IDE로 워크트리 코드를 편집할 때는 그 워크트리를 별도 창으로 열어라.** `.claude/`가 점으로 시작하는 디렉토리라 TypeScript와 ESLint가 기본 탐색에서 건너뛴다 — 저장소 루트를 열어 둔 창에서는 워크트리 파일이 어느 프로젝트에도 속하지 않은 것으로 취급돼 `describe`·`it` 같은 jest 전역을 모르는 이름으로 표시한다. 저장소 루트 `tsconfig.json`에 워크트리를 포함시키는 우회는 쓰지 마라 — 루트에서 `verify`를 돌릴 때 같은 클래스가 두 번 선언된 것으로 보인다.

## 계획 (티어 2)

`architect`에게 넘기는 것은 **셋**이다 — 사용자 요청 **원문**, 워크트리 경로와 브랜치 이름, 사용자가 명시한 제약.

넘기지 않는 것: **네가 미리 세운 구현 방향**(조사 대신 정당화를 하게 된다), **관련 파일 목록**(찾는 것이 그 에이전트의 일이다).

계획서에는 **80줄 상한**이 있다. 그보다 길어야 한다면 작업을 쪼개라는 신호다. 읽는 쪽에도 비용이 든다 — 403줄 계획서를 쓰고 그중 수정 뒤에도 쓰인 것은 판별 단계 하나였던 적이 있다.

**원인이 확정되지 않은 버그는 "진단 노트"로 받는다.** 수정 계획을 미리 쓰지 않고 셋만 적는다 — (1) 원인 후보 목록 (2) **각 후보를 판별하는 방법** (3) 첫 판별 단계. 수정 계획은 판별이 끝난 뒤에 세운다.

### 계획서를 검증한다

**`architect`의 보고를 믿지 않고 계획서를 직접 읽는다.**

| 확인 | 방법 |
|---|---|
| 파일 경로가 실재하는가 | `(신규)`가 아닌 경로를 `ls`로 확인 |
| 단계마다 verify가 통과할 수 있는 크기인가 | 각 단계의 "완료 판정"을 읽는다 |
| 확정하지 못한 요구사항이 있는가 | 계획서 1절 |
| (병렬로 갈 때만) 그룹의 파일 집합이 서로소인가 | 목록을 **직접 대조**. 구현 파일과 테스트 파일이 다른 그룹에 갈라진 것도 겹침으로 센다 |

통과하지 못하면 **`SendMessage`로 같은 `architect`에게 돌려보낸다.** 새로 띄우면 조사를 다시 모은다.

**확정하지 못한 요구사항이 남아 있으면 멈추고 사용자에게 묻는다.** 계획서 1절이 비어 있어도, 후보 중에 `이것이 사실이면 버그가 아니다`류가 있으면 묻는다 — 사실이면 구현 전체가 헛일이 되므로 묻는 비용이 더 싸다.

승인 관문은 없다. 물을 것이 없으면 계획서 경로·단계 목록·배치를 짧게 출력하고 바로 루프로 넘어간다.

**병렬은 기본이 아니다.** 대부분의 작업은 단일 트랙이 맞다. 트랙을 나누기로 정했을 때만 `.claude/ref/parallel.md`를 읽는다.

## 루프

1. **`developer`에게 구현을 맡긴다.** 티어 2면 요청 원문 대신 **계획서 경로와 맡을 단계**를 준다. 라운드마다 새로 띄우지 말고 `SendMessage`로 같은 에이전트를 이어 쓴다 — 자기가 쓴 코드의 맥락이 있어야 지적을 제대로 반영한다
2. **`reviewer`에게 검토를 맡긴다.** 넘기는 것은 **원래 목표**, **diff 위치와 비교 기준**, (티어 2면) **계획서 경로와 맡은 단계**뿐이다. **`developer`의 보고서를 넘기지 마라** — 구현자의 서술이 출발점이 되면 "괜찮다"고 적힌 부분을 덜 보게 된다. 라운드마다 **새로 띄우고**, 대신 **이미 해결된 지적 목록**을 함께 준다
3. **지적을 그대로 옮긴다.** 미리 걸러내지 않는다. 무엇이 진짜 문제인지는 코드를 쥔 쪽이 더 잘 판단한다
4. **반박이 나오면 오케스트레이터가 판단한다.** 같은 지적을 그대로 되돌려 보내면 무한 루프가 된다. 타당하면 해결된 것으로 처리하고 다음 라운드의 "이미 해결됨"에 넣는다. 판단이 서지 않으면 사용자에게 묻는다
5. **`blocker`와 `major`가 하나도 없으면 끝난다.** `minor`가 남아도 통과다. 남은 `minor`는 PR 본문에 적어 사용자가 판단하게 한다

**한 트랙 안에서 두 에이전트를 동시에 띄우지 않는다.** 검토 대상이 확정되지 않은 채 리뷰가 시작된다. `architect`와 `developer`도 마찬가지다.

**3라운드까지 돌고도 `blocker`나 `major`가 남으면 멈추고 사용자에게 보고한다.** 같은 지적이 반복되면 4번을 지키지 않은 것이고, 고칠 때마다 새 지적이 나오면 목표가 애매한 것이다.

### 검토 대상을 고정한다

```bash
.claude/scripts/fingerprint.sh          # 리뷰 시작 전
.claude/scripts/fingerprint.sh          # 리뷰 결과를 받은 뒤 · 커밋 직전
```

**세 값이 같아야 그 판정이 커밋에 유효하다.** 다르면 리뷰어가 본 것과 지금 코드가 달라, 그 판정으로 지적을 넘기거나 커밋해서는 안 된다. 리뷰어에게도 판정 기준 지문을 보고에 적도록 요구한다.

스크립트가 `git add -N`을 앞에 둔다 — **`git diff | shasum`만으로는 추적되지 않는 파일이 지문에서 빠진다.** 손으로 찍지 말고 스크립트를 써라.

## 커밋 · PR

**커밋은 오케스트레이터가 한다.** `developer`는 작업 트리만 남긴다 — 판정 시점 지문과 대조하는 것은 리뷰 결과를 쥔 쪽만 할 수 있다.

```bash
npm run verify                                   # lint → prettier → typecheck. 2초. pre-commit 훅도 이것을 돌린다
git add src/todos/todo-templates.repository.ts src/todos/CONTEXT.md
git commit
git push -u origin feature/step-goal-presets
gh pr create --base develop                      # base를 반드시 명시한다
```

- **의미 단위로 나눈다.** 기본 단위는 계획서의 단계 하나, 계획이 없었으면 "한 문장으로 설명되는 변경 하나". **`git add -A`를 습관으로 쓰지 않는다**
- **각 커밋 시점에 `npm run verify`가 통과해야 한다.** `--no-verify`로 우회하지 않는다
- **테스트와 그것을 통과시키는 구현은 같은 커밋에 넣는다.** TDD는 작업 순서의 규약이고 커밋 분할의 규약이 아니다
- **`CONTEXT.md` 갱신은 그 폴더를 바꾼 커밋에 함께 넣는다**
- **쪼갤 수 없으면 합친다.** 중간 커밋이 verify를 통과할 수 없으면 하나의 커밋이다
- 제목은 한국어로 무엇을 했는지, 본문에는 **왜**를 적는다. 무엇을 바꿨는지는 diff가 말한다

### pre-commit 훅의 사각지대

**훅은 작업트리를 검사한다. 인덱스가 아니다.** `npm run verify`가 프로젝트 전역을 보기 때문이고, 이것이 양쪽으로 어긋난다.

- **깨진 것이 통과한다.** 스테이징한 내용이 verify를 통과하지 못하는데 작업트리에서 이미 고쳐 놨다면 훅은 그대로 통과한다. 위의 "각 커밋 시점에 verify가 통과해야 한다"를 **훅이 보장해 주지 않는다** — 부분 스테이징으로 나눠 커밋한 뒤에는 직접 확인해라
- **정상인 것이 막힌다.** 커밋 대상은 깨끗한데 스테이징하지 않은 작업 중인 파일이 verify를 깨뜨리면 커밋이 거부된다. 위의 "의미 단위로 나눈다"를 지키려 할 때 바로 걸리는 쪽이다. `--no-verify`는 금지이므로 **`git stash -k -u`**로 치운 뒤 커밋하고 `git stash pop`으로 되돌린다. **`-u`를 빼지 마라** — `git stash`는 기본적으로 추적되지 않은 파일을 치우지 않아서, 새로 만든 파일이 원인이면 `-k`만으로는 훅이 또 실패한다. TDD로 새 테스트와 새 구현을 함께 만드는 상황이 정확히 여기에 걸린다

두 사각지대는 스테이징된 내용만 꺼내 검사하지 않는 한 없어지지 않는다(`lint-staged`가 하는 일). 도입은 결정된 바 없다.

**PR 본문에 적을 것**: 리뷰 라운드 수와 무엇이 지적돼 고쳐졌는지, 남은 `minor` 전체, **규약에 남길 값어치가 있는 것**. `docs/`는 추적되지 않으므로 남길 값어치가 있는 것은 PR 본문에 올려야 살아남는다.

정리는 PR이 머지된 뒤에 한다.

```bash
.claude/scripts/worktree-drop.sh step-goal-presets     # docs/를 저장소 루트로 꺼낸 뒤 정리한다
```

## 쓰는 방식 — 축약하지 않는다

**이 규칙은 코드 주석만이 아니라 내놓는 글 전부에 적용된다.** 사용자 응답, 커밋 메시지, PR 본문, 리뷰 답글, 계획서, `CONTEXT.md`, 에이전트끼리 주고받는 보고까지다. 커밋 메시지와 PR 본문은 **저장소에 영구히 남으므로** 특히 그렇다.

**축약어를 쓰지 않는 것이 기본이다.** 줄여서 아끼는 글자 수보다, 읽는 사람이 멈춰서 되짚는 비용이 크다.

- **처음 한 번 풀고 그 뒤로 줄이는 것도 안 된다.** 그러면 뒤를 읽는 사람이 앞으로 돌아가 찾아야 한다. 실제로 `RN`을 첫 문장에서 "React Native"로 풀고 그 뒤 계속 줄여 써서 사용자가 "RN이 뭐야"를 물었다. **같은 글 안에서도 반복해서 풀어 쓴다** — 표·목록·코드 블록 주석에서 다시 나올 때는 특히
- **줄일 수밖에 없다면 괄호로 원어를 붙인다.** `RNTL(React Native Testing Library)`처럼
- **널리 쓰이는 것도 이 저장소 밖에서 온 것이면 푼다.** `DTO`, `RLS`, `FK`, `PK`, `TDD`처럼 익숙해 보이는 것도 처음 접하는 사람에게는 암호다
- **오류 코드와 식별자는 그대로 쓰되 뜻을 옆에 적는다.** `P2002`(고유 제약 위반), `P2025`(고칠 행을 찾지 못했다)처럼
- **줄임말로 된 프로젝트 내부 용어도 마찬가지다.** "티어 2", "지문", "관문" 같은 말을 사용자에게 쓸 때는 무엇을 뜻하는지 한 번 적는다

**결론보다 상황을 먼저 쓴다.** "이런 일이 생길 수 있다 → 그래서 이렇게 했다" 순서다. 결론만 압축해 던지면 그 결론이 답하는 질문이 사라진다.

**표는 이미 문장으로 설명한 것을 정리할 때만 쓴다.** 표로 처음 설명하면 각 칸이 무슨 말인지 알 수 없다.

## 코드 작성

- **TDD**(실패하는 테스트를 먼저 쓰고 통과시키는 방식)**로 한다.** 실패하는 테스트를 먼저 쓰고 **실패를 실제로 확인한 뒤** 통과시킨다. 버그 수정은 재현 테스트부터. 상세는 `.claude/rules/testing.md`
- 주석과 문서(JSDoc 등)는 **한국어**로 쓴다. 주석에는 **왜**를 적는다
- `src/` 하위 폴더를 건드리기 전에 그 폴더의 `CONTEXT.md`를 읽고, 끝난 뒤 갱신한다(`.claude/rules/CONTEXT.md`)
- 규칙을 끄거나 낮출 때는 반드시 이유를 주석으로 남긴다
- **Prisma 7은 6과 다르다** — 드라이버 어댑터가 필수이고 `datasource` 블록에 URL이 없으며 `migrate dev`가 클라이언트를 재생성하지 않는다. 스키마·마이그레이션을 건드리기 전에 `src/prisma/CONTEXT.md`를 읽어라

## 기록 (티어 2만)

`docs/dev-loop/{YYYY-MM-DD}-{브랜치 이름에서 feature/를 뗀 부분}.md`에 남긴다. `worktree-new.sh`가 헤더까지 만들어 두므로 **내용만 채운다.**

**100줄 상한.** 넷만 적는다.

- **목표** — 사용자가 요청한 것 그대로
- **판단이 갈린 지점과 결론** — 반박이 나왔을 때 어느 쪽 손을 들었고 왜 그랬는지. **가장 나중에 다시 볼 값어치가 큰 부분이다**
- **넘긴 `minor`**
- **절차에서 나온 것** — 다음 루프에 반영할 값어치가 있는 것

적지 않는 것: `verify` 출력 원문, 지문 이력, 에이전트 보고서 요약, 이미 계획서에 있는 내용. **라운드가 끝날 때마다 그 자리에서 덧붙인다** — 마지막에 몰아 쓰면 루프가 끊길 때 통째로 날아간다.

## 멈출 때와 끝날 때는 알림을 보낸다

`AskUserQuestion`은 **터미널 안에서만 뜬다.** 이 루프는 서브에이전트 하나가 수 분에서 십수 분을 쓰므로 **그 사이 사용자가 떠나 있는 것이 기본값**이다. 아래 세 자리에서는 재지 말고 `PushNotification`을 함께 보낸다.

- 확인이 필요해 멈출 때 (가장 값어치 있는 알림이다)
- 루프가 끝나 PR을 냈을 때
- 3라운드를 넘겨 사용자 판단이 필요할 때

메시지는 200자 아래 한 줄로, **무엇을 결정해야 하는지를 앞에 둔다.** 사용자가 터미널을 보고 있으면 도구가 스스로 스킵한다. 라운드마다 진행을 알리지는 않는다 — 필요 없는 알림이 쌓이면 정작 필요한 알림을 무시하게 된다.

## 오케스트레이터가 하지 않을 것

- **직접 구현하지 않는다.** 메인 세션이 짠 코드는 리뷰 대상에서 빠진다
- **직접 계획서를 쓰지 않는다.** 조사와 설계를 메인 세션이 하면 그 판단이 검토 없이 구현으로 넘어간다
- **지적을 미리 걸러내지 않는다**
- **`developer`의 보고서를 `reviewer`에게 넘기지 않는다**
- **에이전트의 보고를 그대로 믿지 않는다.** 특히 "다 됐다"는 `reviewer`의 verify 실행 결과로 확인한다
- **같은 대상에 두 에이전트를 동시에 띄우지 않는다**
- **남이 점유한 워크트리를 임의로 이어받지 않는다**
- **사용자를 기다리며 멈출 때 알림 없이 두지 않는다**
