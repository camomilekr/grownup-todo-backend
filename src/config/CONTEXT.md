# CONTEXT

> 마지막 업데이트: 2026-08-17

## 역할

기동 시점에 환경변수를 검증하고 정규화한다. 값이 없거나 형식이 틀리면 **부팅을 실패시킨다.**

## 주요 파일

| 파일명 | 역할 |
|--------|------|
| `env.validation.ts` | `validateEnv`. `ConfigModule.forRoot({ validate })`에 걸린다 |
| `env.validation.spec.ts` | 분기별 테스트 |
| `deployment-port.spec.ts` | 코드 밖 배포 설정(`Dockerfile`의 EXPOSE, Deployment의 `PORT`·`containerPort`, Service 포트)이 기본 포트와 일치하는지 대조한다. 짝이 되는 소스 파일이 없는 spec이다 |

## 핵심 로직

**반환값이 설정 객체를 교체한다.** `ConfigModule`은 `validate`가 돌려준 것을 그대로 설정 원본으로 쓴다. 검증한 키만 돌려주면 나머지 환경변수가 `ConfigService`에서 조용히 사라지므로, 원본을 펼쳐서(`{ ...config }`) 함께 넘긴다. 이 동작을 고정하는 테스트가 있다 — 지우지 마라.

**검증하는 것은 `DATABASE_URL`(필수)과 정수 환경변수 둘(`PORT`·`SHUTDOWN_DRAIN_DELAY_MS`, 모두 선택)이다.** `DIRECT_URL`은 Prisma CLI(마이그레이션)만 쓰는 값이라 런타임 배포 환경에 없는 것이 정상이다. 여기서 필수로 걸면 마이그레이션을 돌리지 않는 환경의 부팅이 막힌다.

**`PORT`는 여기서 기본값(4080)을 채우고 숫자로 바꾼다.** 값을 읽는 `main.ts`가 아니라 여기에 두는 이유가 둘이다 — ① 잘못된 포트를 리슨 시점이 아니라 **부팅 시점**에 세운다(이 폴더의 존재 이유와 같은 근거) ② `process.env`의 값은 언제나 문자열이라, 변환을 소비 지점마다 반복하면 한 곳이 빠졌을 때 문자열이 그대로 샌다. `ConfigService.get`은 `validate`가 돌려준 값을 `process.env`보다 **먼저** 본다(`getFromValidatedEnv` → `getFromProcessEnv` 순서, @nestjs/config 4.x 소스 확인) — 그래서 소비 쪽은 `getOrThrow<number>('PORT')`로 숫자를 받는다. 빈 문자열(앞뒤 공백만 있는 값 포함)을 기본값으로 보는 이유는 `.env.example`이 `PORT=`로 비워 두고 있어, 그것을 그대로 복사한 `.env`가 부팅을 막지 않게 하기 위해서다. 범위는 1~65535이고 0은 거절한다 — Node에서 0은 "빈 포트를 아무거나"라 서버 설정으로는 오류다. **받는 표기는 10진수 정수뿐이다** — `Number()`에 그대로 넘기면 `0x10`(=16)·`8e3`(=8000)·`+8080`이 조용히 통과해, 문서가 약속한 것과 다른 포트로 뜨고도 아무 신호가 없다. 그래서 `/^\d+$/`를 먼저 통과시킨다.

**정수 환경변수는 `parseIntegerEnv` 한 곳을 지난다.** 명세(`이름`·`기본값`·`min`·`max`)만 다르고 규칙은 같다 — 빈 값은 기본값, 표기는 10진수 정수만, 범위 밖은 부팅 실패. 변수마다 파서를 따로 두면 "빈 값을 기본값으로 본다" 같은 규칙이 한쪽에만 반영되는 날이 온다. **`Number.isInteger` 검사는 일부러 뺐다** — `/^\d+$/`를 통과한 값은 항상 정수라 판정에 관여하지 못하는 조건이었고, 남겨 두면 읽는 사람이 "정규식이 막지 못하는 무언가가 있다"고 오해한다.

**기본 포트 상수는 export하지 않는다.** `deployment-port.spec.ts`가 그것을 필요로 하지만, 테스트를 위해 내부 상수를 열지 않고 `validateEnv({ DATABASE_URL })`를 불러 `PORT`를 받는다 — 매니페스트가 맞춰야 하는 것은 "코드에 적힌 숫자"가 아니라 **`PORT`를 주지 않았을 때 애플리케이션이 실제로 여는 포트**이고, 검증 함수를 지난 값이 바로 그것이다. 기본값을 채우는 코드가 사라지는 회귀도 이 경로에서만 걸린다.

**`SHUTDOWN_DRAIN_DELAY_MS`는 `PORT`와 하한이 다르다.** 0이 유효하다 — 매니페스트가 `preStop: sleep`으로 대기를 대신하기로 하면 앱 내부 대기를 꺼야 한다. 이 저장소의 매니페스트는 그 반대를 택해 `preStop`을 두지 않고 8000을 주입한다(`k8s/deployment.yaml`). **상한 60000이 막는 것은 자릿수 오타(`5000`을 `500000`으로 적는 류)까지다** — 이 검증을 통과했다고 `terminationGracePeriodSeconds`와 양립한다는 뜻이 아니다. 상한값 60초에 자원 해제 예산(`DISPOSE_TIMEOUT_MS` 10초)만 더해도 k8s 기본 유예 30초를 넘으므로, 허용 범위 안의 값으로도 SIGKILL이 드레인 중간을 자를 수 있다. **유예 기간과의 양립은 검증이 아니라 매니페스트가 맞춰야 하고**, 맞춰야 할 조건은 `src/health/CONTEXT.md`의 "매니페스트가 만족해야 할 조건"에 있다. 소비하는 곳은 `src/shutdown/shutdown-registry.service.ts`다.

**경계값은 "받는다" 쪽도 단정한다.** 바깥을 던지는 단정만 있으면 부등호를 한 칸 밀어도(`<` → `<=`) 전부 통과한다 — 실제로 밀어 보고 4건이 실패하는 것을 확인했다(2026-08-12).

**에러 메시지에 값을 싣는 기준은 비밀값 여부다.** `DATABASE_URL`은 접속 문자열에 DB 비밀번호가 들어 있어 값을 싣지 않는다 — 부팅 실패 로그가 그대로 비밀값 유출이 된다. `PORT`·`SHUTDOWN_DRAIN_DELAY_MS`는 비밀값이 아니므로 값을 실어 원인을 좁혀 준다.

`postgresql://`과 `postgres://`를 모두 받는다. libpq와 Supabase 문서가 두 스킴을 섞어 쓴다.

## 의존성

없다. 순수 함수 하나이고 `@nestjs/config`에도 의존하지 않는다 — 그래서 테스트에 컨테이너가 필요 없다. 이 함수를 물리는 곳은 `src/app.module.ts`다.
