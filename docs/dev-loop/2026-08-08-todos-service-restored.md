## 목표

두 테이블(`todoTemplate` 정의 · `todoHistory` 기록)에 나뉘어 저장된 할 일을 부르는 쪽에서 하나로 보게 하는 Service 계층. 조회 세 종과 쓰기 여섯 종을 `TodosService`가 제공하고, 소유자 검사가 처음으로 들어갔다. 이후 같은 브랜치에서 활성 기간의 timestamptz 반열림 전환, 병합 목록(`listTodosOn`), 코파일럿 리뷰 대응까지 진행했다.

## 판단이 갈린 지점과 결론

- **이력을 배열로 항상 붙이는 대신 `progress` 단일 객체로 내보낸다.** 일회성의 날짜 키는 화면용이 아니고, 매일 반복은 기록이 무한히 늘어 목록 페이로드가 커지며, "오늘 할 일" 화면에 필요한 것은 그날 하루의 상태 하나다. 이력 배열은 상세 조회에만 두고 기간 범위로 좁힌다
- **일회성 목록 조회의 필터를 버리지 않고 `include`만 추가했다.** 필터가 하는 일은 완료 판정이 아니라 목록 규칙 자체의 표현이다 — 일회성은 완료하면 사라지고 매일 반복은 남는다
- **완료 자동 처리를 넣지 않았다.** 진행값과 완료 여부를 한 저장 경로가 동시에 바꾸면, 잘못 입력한 진행값에 완료가 딸려 오고 되돌리려면 두 번 고쳐야 한다
- **Repository에 소유자를 인자로 추가했다.** Service가 조회 후 비교하는 방식은 새 메서드에서 비교를 잊을 수 있고, 인자면 빠뜨리는 것 자체가 컴파일되지 않는다
- **활성 기간은 반열림으로 확정했다(사용자 결정)** — `activeFrom <= 순간 < activeUntil`. PR #8(양 끝 포함, `gte`)과 갈래가 갈렸던 것을 통합하며 마이그레이션 계보를 `20260805123230` 하나로 단일화했다. `20260805111110`을 이미 적용한 다른 환경이 있다면 유령 이력이 되는데, 당시 개발 데이터베이스 하나뿐임을 실측으로 확인했다
- **병합 목록의 정렬 규칙(사용자 확정)**: 마감 순간 오름차순 — 일회성은 `shouldDoAt`, 매일 반복은 유저 타임존 기준 **다음 달력 날짜가 시작되는 최초의 순간**(오늘 마감 취급), 예정일 없는 일회성은 맨 뒤. 동률은 `createdAt`·`todoId`. 완료 여부는 반영하지 않는다 — 완료 토글마다 목록이 재배열되면 화면이 튄다
- **마감 계산의 계약을 "다음 자정"이 아니라 "다음 달력 날짜가 시작되는 최초의 순간"으로 정의했다.** DST(일광 절약 시간) 전환일에는 자정이 없거나 두 번 있다. 구현이 기대는 단조성 가정은 IANA 타임존 418개 × 500일 전수 실측으로 확인했다
- **재작업(사용자가 구조 결정을 뒤집음)**: `listTodosOn`이 Repository 직접 호출 대신 `listOnce` + `listDailyAt`을 재사용한다 — 비즈니스 로직 중복 회피가 우선. `TodoListItem`에 `createdAt`을 열었고 상세 두 갈래에는 열지 않았다 — 응답 필드는 한 번 나가면 걷기 어렵다
- **동시 부분 갱신 경쟁은 DB CHECK 제약으로 닫았다(사용자 확정).** `active_from < active_until` 제약을 추가하고, 경쟁 패자가 받는 위반(`P2039`, SQLSTATE `23514`)을 `updateTodo`에서 409로 변환한다. 동시 요청 재현 테스트는 의도적으로 없다 — 타이밍 의존 테스트는 간헐 실패를 만든다

## 리뷰 경과

Service 본작업 11라운드(`major` 10건 전부 반영), timestamptz 통합 2+1라운드, 병합 목록 1라운드, 재작업 2라운드, 코파일럿 대응 1라운드. 실제 장애를 막은 것 둘 — `strictNullChecks`가 꺼져 있어 `histories[0]`의 `undefined`가 통과해 가장 흔한 상태에서 목록 조회가 500이 될 뻔한 것(게다가 완료 여부가 `true`로 뒤집혀 조용히 틀리는 상태), 오류 처리기가 처리하려던 값을 다시 읽어 스스로 `TypeError`를 던지던 것. 가장 오래 붙은 문제는 소유자 검사 도입으로 한 컬럼 값의 옳은 출처가 뒤집혔는데 옛 지시가 여섯 계층(코드 주석·스키마 주석·폴더 문서 둘·저장소 문서·마이그레이션 SQL·데이터베이스 컬럼 코멘트)에 복제돼 있던 것 — 어떤 자동 관문도 잡지 못한다.

**남은 `minor`: 없음.** 병합 시점 기준 전부 반영됐다.

## 절차에서 나온 것 (규약에 남길 값어치)

- 같은 서술을 고칠 때 저장소 `grep`만으로는 부족하다 — 데이터베이스 코멘트와 `prisma generate` 산출물까지 본다. 사본이 몇 곳인지 숫자를 세어 적지 마라 — 그 숫자가 다시 검증 대상이 된다
- 코드만으로 검증할 수 없는 서술(값의 출처·사본 위치·미래 예고)이 어긋난다. 미래를 예고하는 문장에는 유효기간이 있다 — 지울 시점을 함께 정하고, 정할 수 없으면 쓰지 않는다
- 주석으로 계약을 선언하는 것과 지키는 것은 다른 일이다 — "`0`도 유효한 입력"이라는 주석에 `0`을 넘기는 테스트가 없었다
- 변이 주입이 이미 통과하는 테스트를 검토할 수 있는 유일한 방법이다. 확인할 것 넷 — 치환 대상의 유일성, `Tests: 0 total`이 아닌지, 깨진 것이 의도한 테스트인지, 되돌린 뒤 통과 재확인
- 값의 유출을 부분 문자열로 잡을 때는 그 값이 문자열이 되는 형태를 센다 — `Date`의 로컬 표현에는 `YYYY-MM-DD`가 없다
- `worktree-new.sh`가 `.env`를 복사하지 않아 e2e를 돌릴 수 없었다 — `.env`도 복제 대상이다
- 지문과 `npm` 명령에 워크트리 경로를 명시한다 — 셸 위치가 도구 호출 사이에 루트로 돌아간다
- 한 에이전트에게 다섯 단계를 연속으로 맡기면 멈출 수 있다 — 지적 반영은 이어 쓰고 새 단계는 새로 띄운다. 이어받을 때는 타입 오류가 "미완성"인지 "깨짐"인지 구분한다
- 의미가 뒤집히는 머지에서는 충돌 없이 병합된 파일의 서술도 검토 대상이다 — 충돌 해소 diff에는 나타나지 않는다
- jest 워커가 실패 diff의 `bigint`를 직렬화하지 못한다 — `--runInBand`로 우회 (`.claude/ref/testing-traps.md`에 반영됨)
- CHECK 제약은 Prisma 스키마 언어로 표현하지 못해 SQL을 손으로 넣은 세 번째 항목이다(RLS·컬럼 코멘트에 이어) — drift 검사가 CHECK를 비교하지 않는다

## 별도 작업으로 넘긴 것

- `strictNullChecks` 켜기 — 이 작업에서 두 번 실제 결함을 만들었고 둘 다 컴파일러가 잡을 수 있었다. 기존 코드 전체가 진단 대상이 되므로 범위가 크다
- Controller · 요청 DTO(Data Transfer Object, 요청·응답 형태를 담는 클래스) · 전역 `ValidationPipe` · 전역 `ExceptionFilter` · `remindAt`의 `HH:mm` 검증 · 타임존 이름 유효성 검증 · 진행값 범위 검증(음수 거절) — 값을 받는 경계의 책임이라 Controller 라운드에서 함께 정한다
