# todo 스키마

> 기준: `prisma/schema.prisma` · 마이그레이션 `20260731075406_init_todo_entities`(테이블 생성)와 `20260731164011_fix_todo_history_user_id_comment`(컬럼 코멘트 수정)

## 전체 그림부터

할 일 하나는 **두 개의 테이블**에 나뉘어 저장된다. 이 구조를 먼저 이해하면 나머지는 쉽다.

**`todoTemplate`은 할 일의 정의다.** "매일 물 2리터 마시기" 같은 내용이 여기 있다. 제목, 설명, 목표 수치, 알림 시각처럼 **사용자가 보고 고치는 것은 전부 이쪽**이다. 할 일을 만들면 이 행이 하나 생긴다.

**`todoHistory`는 그 할 일을 실제로 수행한 완료 기록이다.** 언제 얼마나 했는지만 담고, 할 일의 내용은 담지 않는다. 그래서 화면에 제목을 보여 주려면 두 테이블을 함께 읽어야 한다.

왜 이렇게 나눴는가. 할 일의 정의는 계속 바뀔 수 있지만(제목 수정, 목표 상향 등) **이미 지나간 날의 기록은 그대로 남아야 하기 때문**이다. 반대로 기록 쪽에 내용을 복사해 두면 제목을 한 번 고칠 때마다 과거 기록과 현재 정의가 서로 어긋난다. 그래서 **내용은 정의에만, 실적은 기록에만** 둔다.

기록에는 중요한 성질이 하나 더 있다. **완료하거나 진행값을 입력할 때 비로소 행이 만들어진다.** 미리 만들어 두지 않기 때문에 **"그날 행이 없다"가 곧 "그날 아무것도 하지 않았다"**는 뜻이 된다.

```
appUser ──┬─< todoTemplate ──< todoHistory
          └─< todoHistory          ▲
                두 컬럼을 묶은 외래키 (todoId, userId) ┘
```

## enum 두 가지

**`CompleteType` — 한 번만 하는 일인가, 매일 반복하는 일인가.**

| 값 | 뜻 | 목록에서 어떻게 동작하는가 |
|---|---|---|
| `ONCE` | 일회성 | 완료할 때까지 계속 나온다. 예정일이 지나도 사라지지 않고, 완료해야 사라진다 |
| `DAILY` | 매일 반복 | 어제 안 했더라도 어제는 미완료로 남고, 오늘은 오늘대로 다시 나온다 (밀린 일이 쌓이지 않는다) |

**`TodoType` — 무엇으로 달성하는가.**

| 값 | 뜻 |
|---|---|
| `GENERAL` | 일반. 체크하면 끝이다 |
| `NUMERIC` | 숫자형. 목표 수치를 정하고 그만큼 채우면 완료다 |
| `STEPS` | 걸음수. `NUMERIC`과 구조가 같고 값의 출처만 다르다 (사용자 입력이 아니라 건강 데이터) |

`STEPS` 전용 컬럼은 따로 없다. 타입이 늘 때마다 컬럼을 추가하면 대부분이 비어 있는 테이블이 되기 때문이고, 세 타입이 `targetValue`(목표치)와 `targetUnit`(단위) 한 쌍을 함께 쓰는 것으로 충분하다. "걸음"·"분" 같은 단위는 enum이 아니라 `targetUnit` 문자열이 담는다.

## appUser

> 테이블 `app_user` — `user`가 Postgres 예약어라 접두사를 붙였다.

할 일의 소유자다. Supabase가 자체적으로 관리하는 `auth.users` 테이블은 참조하지 않는다. 참조하려면 Prisma의 `multiSchema` 기능을 켜야 하는데, 켜는 순간 Supabase가 만든 auth·storage 등 여러 스키마가 마이그레이션 비교 대상으로 올라오기 때문이다.

| field name | db column | type | not null | constraint | 설명 |
|---|---|---|---|---|---|
| `userId` | `user_id` | `BIGSERIAL` | true | PK | id |
| `email` | `email` | `varchar(320)` | true | UNIQUE | 이메일. 320자는 이메일 주소의 최대 길이(RFC 5321)다 |
| `timeZone` | `time_zone` | `varchar(64)` | true | 기본값 `Asia/Seoul` | 사는 지역의 시간대. 매일 반복 할 일의 "오늘"이 언제 바뀌는지를 정한다 |
| `createdAt` | `created_at` | `timestamptz(3)` | true | 기본값 `now()` | 가입 일시 |
| `updatedAt` | `updated_at` | `timestamptz(3)` | true | 자동 갱신 | 마지막으로 고친 일시 |
| `deletedAt` | `deleted_at` | `timestamptz(3)` | false | | 탈퇴 일시. 값이 있으면 탈퇴한 유저다 |

**이메일에 걸리는 함정이 둘 있다.**

첫째, **저장하기 전에 소문자로 바꿔야 한다.** Postgres의 문자열 비교는 대소문자를 구분하므로 `Foo@x.com`과 `foo@x.com`이 서로 다른 값이 되고, 같은 사람이 계정 두 개를 갖게 된다. 이것을 강제하는 코드는 아직 없다.

둘째, **탈퇴한 뒤 같은 이메일로 다시 가입하면 중복 오류가 난다.** 탈퇴는 행을 지우지 않고 `deletedAt`에 시각을 적는 방식인데, 이메일 중복 검사는 그 행까지 포함해서 하기 때문이다. 그런데 일반 조회는 `deletedAt`이 비어 있는 행만 보므로 **화면에서는 그 유저가 존재하지 않는 것처럼 보인다.** 원인을 찾으려면 DB를 직접 봐야 한다. 그래서 가입 처리만큼은 탈퇴한 행까지 찾아본 뒤 되살릴지 거절할지 정해야 한다.

## todoTemplate

> 테이블 `todo_template`

할 일의 정의다. **할 일의 내용은 전부 여기에만 있고**, 제목·설명·목표치·알림 시각을 고치려면 이 행을 수정한다.

완료 시각은 여기에 두지 않는다. 일회성 할 일도 완료 여부는 "수행 기록이 있는가"로 판단하는데, 여기에도 완료 시각을 두면 같은 사실이 두 곳에 기록되어 둘이 어긋났을 때 어느 쪽이 맞는지 알 수 없어지기 때문이다.

| field name | db column | type | not null | constraint | 설명 |
|---|---|---|---|---|---|
| `todoId` | `todo_id` | `BIGSERIAL` | true | PK | id |
| `userId` | `user_id` | `bigint` | true | FK → `app_user` | 소유자 |
| `title` | `title` | `varchar(200)` | true | | 할 일 제목 |
| `description` | `description` | `text` | false | | 설명 (markdown 문서) |
| `todoType` | `todo_type` | `todo_type` | true | **수정 불가** | 무엇으로 달성하는가 |
| `completeType` | `complete_type` | `complete_type` | true | **수정 불가** | 한 번만 하는가 매일 하는가 |
| `remindAt` | `remind_at` | `varchar(5)` | false | | 알림 시각 (HH:mm, 유저 타임존 기준) |
| `shouldDoAt` | `should_do_at` | `timestamptz(3)` | false | | 언제까지 해야 하는지. **일회성 전용** |
| `targetValue` | `target_value` | `numeric(12,2)` | false | | 목표 수치. 일반 타입에서는 비어 있다 |
| `targetUnit` | `target_unit` | `varchar(16)` | false | | 목표 수치의 단위 ("걸음", "잔") |
| `activeFrom` | `active_from` | `date` | false | | 반복 시작일 (이 날 포함). **매일 반복 전용** |
| `activeUntil` | `active_until` | `date` | false | | 반복 종료일 (이 날 포함). 비어 있으면 무기한 |
| `createdAt` | `created_at` | `timestamptz(3)` | true | 기본값 `now()` | 만든 일시 |
| `updatedAt` | `updated_at` | `timestamptz(3)` | true | 자동 갱신 | 마지막으로 고친 일시 |
| `deletedAt` | `deleted_at` | `timestamptz(3)` | false | | 삭제 일시. 행은 남겨 둔다 |

**제약과 인덱스**

| | 대상 | 이유 |
|---|---|---|
| UNIQUE | `(todo_id, user_id)` | `todoId`만으로도 행이 정해지므로 논리적으로는 중복이다. `todoHistory`가 이 두 컬럼을 묶어 참조하는데, Postgres가 그런 참조의 대상 쪽에 같은 조합의 유일 제약을 요구해서 둔다 |
| INDEX | `(user_id, deleted_at)` | 목록 조회 두 가지가 모두 `userId`로 좁히고 삭제되지 않은 것만 보므로 함께 묶었다 |

### 종류와 반복 방식은 만든 뒤 바꿀 수 없다

사용자가 확정한 요구다. **두 값 모두 완료 기록에 저장되지 않아서, 이미 쌓인 기록을 해석하는 근거가 이 정의 하나뿐이라는 것이 공통된 이유다.** 무엇이 어긋나는지가 다르다.

**`todoType`을 바꾸면** 지나간 기록의 해석이 통째로 달라진다. 완료 기록에는 종류가 저장되지 않으므로, 과거 기록을 화면에 그릴 때 "무슨 종류의 기록인가"를 판단하는 근거가 이 컬럼 하나뿐이기 때문이다. 숫자형에서 일반으로 바꾸면 목표치를 가진 과거 기록이 "체크만 하는 할 일"의 기록으로 표시되고, 반대 방향이면 목표치가 비어 있는 기록에 진행률을 그리려 한다.

목표치와 단위 자체는 기록에 복사돼 있어 흔들리지 않는다. **흔들리는 것은 그 값을 무엇으로 읽을지다.**

**`completeType`을 바꾸면** 완료 기록의 날짜를 만드는 규칙이 달라진다(아래 `historiedOn` 설명 참고). 게다가 **완료 기록에는 반복 방식이 저장되지 않으므로**, 이미 쌓인 날짜들을 해석할 근거가 이 컬럼 하나뿐이다. 여기서 바꾸면 과거 기록의 날짜가 무슨 의미였는지 알아낼 방법이 없어진다.

막는 것은 DB 제약이 아니라 TypeScript 타입이다(`UpdateTodoTemplateInput`에서 두 필드를 제외했다). 그래서 그 제외가 사라지면 컴파일만 실패하고 DB는 조용히 허용한다 — `test/todos.e2e-spec.ts`가 그 컴파일 오류의 존재를 붙잡아 둔다.

### 일시 중지 기능은 없다

"잠시 쉬었다가 재개"는 지원하지 않기로 했다(사용자 확정). 반복을 멈추려면 `activeUntil`로 기간을 끝내거나 할 일을 삭제한다.

## todoHistory

> 테이블 `todo_history`

할 일을 실제로 수행한 **완료 기록**이다. **할 일의 내용은 여기에 없다** — 제목·설명·종류·알림 시각은 전부 `todoTemplate`에 있고, 이 테이블은 "언제 얼마나 했는가"만 담는다.

예외가 목표치 한 쌍이다. 이것만 정의에서 복사해 온다. 이유는 **목표를 5에서 8로 올렸을 때 5를 채웠던 날의 달성률이 100%에서 62%로 소급해 바뀌는 것을 막기 위해서**다. 그날 기준의 목표를 함께 남겨 두면 지나간 기록이 나중 변경에 흔들리지 않는다.

| field name | db column | type | not null | constraint | 설명 |
|---|---|---|---|---|---|
| `todoHistoryId` | `todo_history_id` | `BIGSERIAL` | true | PK | id |
| `todoId` | `todo_id` | `bigint` | true | 묶음 FK | 어떤 할 일의 기록인지 |
| `userId` | `user_id` | `bigint` | true | 묶음 FK + FK → `app_user` | 소유자. **요청자의 식별자를 넣는다** (아래 입력 경계 표) |
| `historiedOn` | `historied_on` | `date` | true | UNIQUE의 일부 | 이 기록이 속한 날짜. **의미가 반복 방식에 따라 갈린다** (아래) |
| `targetValue` | `target_value` | `numeric(12,2)` | false | | 그날 기준의 목표 수치 (정의에서 복사) |
| `targetUnit` | `target_unit` | `varchar(16)` | false | | 그날 기준의 목표 단위 (정의에서 복사) |
| `progressValue` | `progress_value` | `numeric(12,2)` | false | | 그날 실제로 달성한 값. 일반 타입에서는 비어 있다 |
| `completedAt` | `completed_at` | `timestamptz(3)` | false | | 완료 시각. **비어 있지 않으면 완료한 것이다** |
| `createdAt` | `created_at` | `timestamptz(3)` | true | 기본값 `now()` | 기록이 처음 생긴 일시 |
| `updatedAt` | `updated_at` | `timestamptz(3)` | true | 자동 갱신 | 마지막으로 고친 일시 |
| `deletedAt` | `deleted_at` | `timestamptz(3)` | false | | 지워진 일시. **할 일이 지워질 때만 찍힌다** |

### 완료 기록은 지울 수 없다

사용자가 확정한 규칙이다. **기록을 개별적으로 지우는 방법이 없다** — Repository에 그런 메서드를 두지 않았다. `deletedAt`이 찍히는 경우는 **할 일 자체가 지워질 때 하나뿐**이고, 그때 그 할 일의 기록이 한 트랜잭션에서 함께 표시된다.

**완료 취소는 삭제가 아니다.** `completedAt`을 비우는 수정이고 행은 그대로 남는다. 그래서 취소한 뒤 다시 완료할 수 있다.

그 구분이 중요한 이유가 있다. 일회성 할 일의 날짜 키는 할 일 생성 시각에서 나오므로 **슬롯이 평생 하나뿐**인데, 만약 완료 취소가 삭제였다면 그 하나가 지워진 행에 막혀 **영영 완료할 수 없는 할 일**이 된다. 목록에는 계속 보이는데 체크가 안 되는 상태다. 기록을 지울 수 없게 하면서 그 경로 자체가 사라졌다.

**남은 대가**: 할 일이 지워지면 그 기록들도 지워진 것으로 표시되는데, 유일 제약은 지워진 행도 자리를 차지한다. 그래서 **지워진 할 일에는 새 기록을 만들 수 없다.** 저장 경로가 그 경우를 조용히 넘기지 않고 오류로 거절하고, 조회도 지워진 할 일의 기록을 내보내지 않는다.

**제약과 인덱스**

| | 대상 | 이유 |
|---|---|---|
| UNIQUE | `(todo_id, historied_on)` | 같은 할 일에 같은 날짜 기록이 둘 생기지 않게 막는다. 저장할 때 쓰는 "있으면 수정, 없으면 생성" 동작이 이 조합을 기준으로 판단한다. **지워진 행도 이 자리를 계속 차지한다** |
| FK | `(todo_id, user_id)` → `todo_template(todo_id, user_id)` | **두 컬럼을 묶은 외래키다.** 남의 할 일 번호에 자기 유저 번호를 붙인 기록을 삽입 단계에서 거절한다 |
| FK | `user_id` → `app_user(user_id)` | |
| INDEX | `(user_id, historied_on)` | 매일 반복 할 일의 날짜별 조회용 |

완료 여부를 나타내는 참/거짓 컬럼은 두지 않았다. 두 값이 서로 어긋날 수 있고, "완료 시각이 비었는지"라는 규칙 하나면 충분하기 때문이다.

### `historiedOn`의 의미가 반복 방식에 따라 갈린다

값은 반드시 `src/todos/todo-local-date.ts`의 `toHistoriedOn`으로 만든다.

**매일 반복(DAILY)이면** 실제로 수행한 날을 유저 타임존 기준으로 적는다. 이 값이 곧 화면에 보여 주는 날짜다.

**일회성(ONCE)이면 다르다.** 일회성 할 일은 완료 기록이 하나만 있어야 하는데, DB가 가진 장치는 `(todoId, historiedOn)` 유일 제약 하나뿐이다. 즉 날짜가 달라지면 DB는 중복으로 보지 않는다 — 수행한 날을 키로 쓰면 8월 1일에 남긴 기록과 8월 3일에 남긴 기록이 서로 다른 행이 되어 **둘 남는다.** 그래서 이 값을 **절대 바뀌지 않는 것**에서 만들어야 하고, `todoTemplate`의 생성 시각이 그 조건을 만족한다(한 번 정해지면 수정되지 않는다). 예정일은 사용자가 바꿀 수 있고 타임존도 바꿀 수 있어 쓸 수 없다.

| | 무엇이 들어가나 | 화면에 보여 줄 날짜인가 |
|---|---|---|
| `DAILY` | 수행한 날을 **유저 타임존 기준**으로 | **그렇다** |
| `ONCE` | 정의의 생성 시각을 **UTC 기준 날짜**로 | **아니다.** 중복을 막는 열쇠일 뿐이다 |

**일회성에서 잃는 것이 없는 이유**: 일회성 목록은 날짜로 거르지 않고 "완료된 기록이 있는가"만 본다. 예정일은 `shouldDoAt`이, 실제 완료 시점은 `completedAt`이 답한다. 다만 **일회성을 날짜별로 묶어 보여 주는 데 이 컬럼을 쓰면 안 된다.**

## 목록을 어떻게 조회하는가

**두 경우 모두 `todoTemplate`에서 시작한다.** 기록은 완료하거나 진행값을 입력할 때 비로소 생기므로, 기록을 기준으로 찾으면 **아직 손대지 않은 할 일이 전부 빠지기** 때문이다.

| | 조건 | 결과 |
|---|---|---|
| 일회성 | **완료된 기록**(완료 시각이 채워진, 취소되지 않은 기록)이 없는 것 전부. **날짜로 거르지 않는다** | 완료할 때까지 계속 나온다. 진행값만 입력한 상태도 목록에 남는다 |
| 매일 반복 | 그날 활성 기간 안(양 끝 포함). 그날 기록을 0~1개 붙여 준다 | 어제 미완료는 어제로 남고 **오늘로 밀려오지 않는다** |

**완료 여부를 누가 판정하는지가 둘이 다르다.** 일회성의 "아직 완료 안 됨"은 **쿼리 조건 그 자체**라 DB에서 걸러진다. 매일 반복은 기록을 붙여 주기만 하고 **완료 판정은 위 계층(Service)에 남긴다.** 그 차이가 Repository와 Service의 경계다.

**날짜별 기록 조회는 매일 반복만 돌려준다.** 일회성의 `historiedOn`은 화면용 날짜가 아니라서 섞이면 안 되는데, 완료 기록에 반복 방식이 저장되지 않아 결과를 받은 쪽에서 걸러 낼 수 없다. 그래서 Repository의 쿼리 조건으로 못 박아 두었다.

## DB가 검사해 주지 않는 것

아래는 전부 **값을 받는 쪽(DTO·Service)의 책임**이고 아직 강제하는 코드가 없다. 지금은 잘못된 값이 들어가도 DB가 막지 않는다.

| 대상 | 지켜야 할 것 | 어기면 |
|---|---|---|
| `email` | 소문자로 바꾸고 앞뒤 공백 제거 | 같은 사람이 계정 두 개를 갖는다 |
| `time_zone` | IANA 타임존 이름인지 (`Intl.supportedValuesOf('timeZone')`) | **그 유저의 모든 날짜 계산이 계속 실패한다** |
| `remind_at` | `HH:mm` 형식인지 (00~23시, 00~59분). 정규식은 표 아래에 | 알림 대상을 문자열 일치로 찾으므로 **오류 하나 없이 영영 알림이 가지 않는다** |
| `active_from`·`active_until` | `parseLocalDateKey`로 만든 값 | 직접 만든 날짜는 **하루 밀려 저장된다** |
| `todo_history.user_id` | **요청자의 식별자**를 넣는다 (표 아래 설명) | 소유자 검사와 묶음 외래키를 **둘 다 통과해** 남의 할 일에 기록이 쓰인다 |

`todo_history.user_id`는 다른 넷과 성질이 다르다. 형식을 다듬는 문제가 아니라 **값을 어디서 가져오는가**의 문제이고, 어겼을 때 아무 오류도 나지 않는다.

완료 기록을 저장하는 경로(`upsertForHistoriedOn`)가 `(todo_id, user_id)`로 정의를 찾아 **소유자를 검사한다.** 그래서 이 값이 요청자를 가리켜야 남의 할 일에 기록을 붙이려는 요청이 그 자리에서 걸린다. **정의 행에서 읽은 값을 그대로 옮기면 그 검사가 무력화될 수 있다** — 소유자로 좁혀 읽은 정의라면 그 값이 요청자와 같아 결과가 다르지 않지만, 좁히지 않고 읽은 정의에서 가져오면 그 정의와 자기 자신을 비교하는 동어반복이 된다.

**그 경로에서는 묶음 외래키도 통과한다.** 값이 정의와 일치하기 때문이다 — 요청자가 아닌 제3자의 것으로 일치할 뿐이고, 외래키는 값이 맞는지만 보고 어디서 왔는지는 모른다. 두 겹이 모두 뚫리는 유일한 경로다. 실패 경로와 근거는 `src/todos/todo-histories.repository.ts`의 `TodoHistorySnapshot` 주석에 있다.

**실제 데이터베이스의 컬럼 코멘트도 이 방향으로 갱신했다**(마이그레이션 `20260731164011_fix_todo_history_user_id_comment`). 이 방향이 어떻게 뒤집혔는지는 그 파일의 SQL 주석에 있다.

`remind_at`에 쓸 정규식이다. 표 안에 두면 마크다운이 파이프를 열 구분자로 읽어 표가
깨지므로(이스케이프하면 렌더링은 되지만 raw 텍스트에서 복사하면 틀린 식이 된다) 여기에
따로 둔다. **복사해서 그대로 쓰면 된다.**

```ts
@Matches(/^([01]\d|2[0-3]):[0-5]\d$/)
```

## RLS (행 단위 접근 제어)

세 테이블과 `_prisma_migrations`(Prisma의 마이그레이션 이력 테이블) 모두 **RLS가 켜져 있고 정책은 하나도 없다.**

Supabase는 `public` 스키마에 새로 만들어지는 모든 테이블에 `anon`(로그인하지 않은 사용자) 권한을 자동으로 붙인다. 정책이 0개인 상태로 RLS를 켜면 그 권한이 있어도 **어떤 행에도 닿지 못하고**, 백엔드가 쓰는 `postgres` 역할은 RLS를 통과하도록 되어 있어 **영향을 받지 않는다.**

**이 프로젝트는 현재 Data API(DB를 HTTP로 직접 노출하는 기능)가 꺼져 있어서 그 권한에 닿을 경로가 없다.** 지금 뚫려 있는 구멍을 막는 것이 아니라 그 기능을 켜는 날을 위한 대비이고, 백엔드에 아무 영향이 없으므로 비용이 0이다.

**RLS와 컬럼 설명(DB 코멘트)은 Prisma가 표현하지 못해 마이그레이션 SQL에 손으로 넣었다.** `prisma migrate diff`가 둘 다 감지하지 못하므로 마이그레이션을 다시 뽑으면 조용히 사라진다 — `test/schema-guard.e2e-spec.ts`가 `public`의 모든 테이블과 컬럼을 훑어 빠진 것을 잡는다. 목록을 코드에 적어 두지 않았기 때문에 **앞으로 추가되는 테이블에도 자동으로 적용된다.**
